# 开发基本准则 · 可验收版

> 这份文档是**验收标准**，不是参考资料。每条都能查、能打勾、能判不通过。
> 依据：12-Factor App（12factor.net）、数据库备份 3-2-1 原则、行业恢复演练实践，以及本项目 2026-11-27 数据丢失事故。
>
> 定这份文档的原因：数据库放在代码目录里、零备份、还拍胸脯说没问题——这三件都发生了。这些是常识，常识失守说明没纪律，不是没知识。

---

## 一、六条铁律

违反了就是事故，不需要讨论「这次特殊」。

1. **数据文件绝不放在代码目录里。** 部署会重写代码目录，放里面等于每次清库。
2. **有用户数据就必须有备份，且备份必须被验证过能恢复。** 没验证过的备份等于没有。
3. **交付前必须走一遍真实的完整流程。** 部署 → 重新登录 → 数据还在 → 功能可用。少一步都算没做完。
4. **不说「没问题」。** 只说「我验证了什么、没验证什么」。无条件保证一旦落空，比不开口更伤人。
5. **动数据之前先备份。** 迁移、清理、改结构、发布，任何可能碰到生产数据的操作。
6. **改完立刻推到远程仓库，并核对远程确实收到了。** 只留在本机等于没写——本机坏一次就全没。核对方式是比对本地与远程的提交号，不是凭印象说「我推过了」。连文档、规范、笔记一起推，不挑。

## 二、S 级：致命项（违反即事故）

### S1 · 数据与代码物理分离

**要求**：数据库文件、上传文件、密钥，全部放在代码目录之外，通过环境变量指定路径。

**为什么**：容器化/托管平台的部署方式是「替换整个代码目录」。数据在里面 = 每次发布清库。这条是 12-Factor 的「无状态进程 + 后端服务作为附加资源」的直接落地。

**怎么验**：
```bash
# 1. 数据路径必须在代码目录外
python -c "import server; print(server.DB_PATH)"
# 期望输出 ~/.xxx/data.db，而不是 .../项目目录/data.db

# 2. 打包含里不能有数据文件
python -c "import zipfile; print([n for n in zipfile.ZipFile('包名.zip').namelist() if '.db' in n or '.pem' in n])"
# 期望输出 []
```

### S2 · 备份存在，且被验证过能恢复

**要求**：
- 每天自动备份，保留至少 3 份（不同日期）
- 备份文件与生产库不在同一目录
- **至少成功恢复过一次**，并记录「从哪个备份、恢复到什么状态、耗时多少」

**为什么**：3-2-1 原则（3 份副本、2 种介质、1 份异地）。行业共识是 30%–40% 的备份在真需要时恢复不出来——坏道、脚本失效、依赖缺失。只有演练过才知道哪份能用。

**怎么验**：
```bash
ls -la ~/.daily-quadrant/backup-*.db        # 至少有 3 个不同日期
# 恢复演练：把最新备份复制成临时库，读一下人数/任务数
cp ~/.daily-quadrant/backup-<日期>.db /tmp/restore_test.db
sqlite3 /tmp/restore_test.db "SELECT COUNT(*) FROM users; SELECT COUNT(*) FROM states;"
```
**记录在案才算通过**。没记录 = 没做。

#### 恢复演练记录

| 日期 | 场景 | 动作 | 结果 |
|---|---|---|---|
| 2026-11-27 15:50 | 本地容器内 | 造 1 用户 + 2 任务（含 `time` 字段）→ 备份 → **删掉 data.db** → 从 `backup-2026-11-27.db` 恢复 | **通过**：用户 1/1、任务 2/2、`16:00` 时间字段完整 |
| 2026-11-27 15:52 | 备份保留策略 | 预置 5 份历史备份（11-21～11-25）+ 生成今日备份 | **通过**：自动清理为最新 3 份（11-24、11-25、11-27） |

**这次演练查出的缺陷**：备份原来只在服务启动时跑一次，服务长期不重启就永远只有启动那天的库。已改为独立线程每小时检查、当天没备份就补一份。

**局限**：以上是本地演练，证明代码逻辑对。线上因无法进入容器文件系统，改用「探针账号登录 + 接口返回数据」间接验证（见 S4）。两者不能互相替代。

### S3 · 密钥不泄漏

**要求**：数据库密码、SMTP 密码、VAPID 私钥、API Key，一律不进代码、不进版本库、不进打包。

**为什么**：12-Factor 的「配置放环境」——判据是「现在把代码开源，会不会泄漏凭据」。

**怎么验**：
```bash
grep -rn "password\|secret\|token" --include=*.py --include=*.js . | grep -v "getenv\|environ\|input\|placeholder"
cat .gitignore | grep -E "\.db|\.pem|\.env"
```
打包后必须 `ls` 一遍确认没有 `.pem` / `.db` / `.env`。

### S4 · 部署后数据仍在（实证，不是推断）

**要求**：每次发布后，**重新登录一次**，确认账号和任务还在。

**为什么**：「接口返回 200」和「数据还在」是两件事。这次就是接口全绿、库没了。

**怎么验**：
```bash
# 发布后立刻做，不是过一会儿
curl -sS -b cookie.txt -X POST https://<域名>/api/login -d '{"username":"<测试号>","password":"<密码>"}'
# 必须返回成功 + 用户信息，不能只看 HTTP 200
```
**上线前先建一个「持久化探针账号」**，每次发布后用它登录。探针不通 = 发布失败，立即回滚。

### S5 · 动数据前先备份

**要求**：任何可能改动生产数据的操作（迁移、批量修复、改表结构、清理），执行前先复制一份库，并确认复制成功。

**怎么验**：操作前 `cp data.db data.db.before-<操作名>-<时间>`，操作后比对文件存在且大小合理。

## 三、A 级：重要项（不修会持续出问题）

### A1 · 端到端跑通才算完成

**要求**：新增/修改功能后，用真实浏览器走完整用户路径：注册 → 登录 → 主流程 → 刷新 → 数据还在。不只用接口测试。

**为什么**：接口层通过、界面层崩，是最常见的漏。

**怎么验**：脚本化走查（本项目用 Playwright），每次交付前跑一遍，看有没有 `pageerror`。

### A2 · 同一规则只写一份

**要求**：前后端共用的计算规则（提醒提前量、排序权重），必须同源或同一份公式，不能各写一遍。

**为什么**：本项目的提醒提前量前后端各写一份，改了一边忘另一边，导致界面显示和实际推送不一致。

**怎么验**：搜关键词（如 `LEAD`、`bonus`），确认前后端数值表一致；跑一个对照用例，比较两端输出。

### A3 · 界面上的承诺必须兑现

**要求**：任何「将在 X 时间做 Y」的文案，都必须和实际执行路径对齐。如果某条规则会把它拦掉，就不能那么写。

**为什么**：「早六点任务，05:42 提醒」——但 6 点前不推送，这条永远不提醒。承诺落空比不承诺更伤信任。

**怎么验**：列出所有会阻断执行的规则（静默时段、去重、权限），逐个对照界面文案，确认没有互相矛盾。

### A4 · 可回滚

**要求**：每次发布有版本号、有 CHANGELOG、知道上一版是什么、能退回去。

**怎么验**：CHANGELOG 最新条目日期是今天；能说出上一版改了什么；数据目录有发布前备份。

### A5 · 输入边界校验

**要求**：所有外部输入（用户输入、导入文件、API 参数）在入口校验，非法值降级或拒绝，不能让它流到界面。

**为什么**：脏时间「25:99」被原样显示成「25:99 到点」，不崩但很蠢，且会误判。

**怎么验**：故意灌脏数据（非法时间、超长文本、空字段、缺字段），看界面是否降级正常、有无报错。

### A6 · 改 A 不坏 B

**要求**：修改后跑既有回归用例。核心逻辑（解析、排序、计算）要有可重跑的测试脚本。

**怎么验**：跑回归脚本，输出 `N/N PASS`。

### A7 · 依赖与环境显式声明

**要求**：依赖写进清单文件，配置从环境变量读，不依赖「机器上刚好装了」。

**为什么**：12-Factor 第 2 条。换机器/重装就崩，通常都是这条没做。

**怎么验**：新目录拉代码，按清单一条命令装完能跑。

## 四、B 级：习惯项（长期质量）

| 项 | 要求 | 怎么验 |
|---|---|---|
| B1 | 提交前语法检查 | `python -m py_compile` / `node --check` / HTML 解析，全过 |
| B2 | 异常不吞 | 搜 `except: pass`、`catch(e){}`，每处要么记日志要么有注释说明为何可忽略 |
| B3 | 迁移脚本幂等 | 同一脚本跑两次结果一致，不重复插数据 |
| B4 | 文档与代码一致 | 界面上写的规则，代码里真有；反之亦然 |
| B5 | 文案风格统一 | 短句、第一人称、自嘲不喊口号；新文案要读起来像原来那个人写的 |
| B6 | 不留死代码 | 无重复定义、无未使用的常量、无「占位分支」 |

## 五、每次交付前的固定动作

发布前逐条打勾，一条不过就不发。

```
[ ] 1. 数据路径在代码目录外（S1）
[ ] 2. 备份文件存在，且今天有一份（S2）
[ ] 3. 打包内容检查过，无 .db / .pem / .env（S3）
[ ] 4. 语法检查全过（B1）
[ ] 5. 端到端走查通过，零 pageerror（A1）
[ ] 6. 核心回归用例 N/N PASS（A6）
[ ] 7. CHANGELOG 已写，说清改了什么、为什么（A4）
[ ] 8. 推到远程，用 `python sync-check.py` 核对本地与远程提交号一致（铁律 6）
[ ] 9. 发布
[ ] 10. 用探针账号重新登录，确认数据在（S4）
[ ] 11. 抽查一个新功能在线上真的能用
```

第 8 步和「发布」的顺序不能反：先让远程拿到代码，再上线。这样即使发布中途出问题，代码是有据可查的。

第 10 步是 2026-11-27 的教训。**没有第 10 步，前面几步都不算数。**

## 六、验收规则

| 情况 | 判定 |
|---|---|
| S 级任一条不过 | **不通过**，立即停止交付并回滚 |
| S 级全过、A 级有 1–2 条不过 | 有条件通过，必须在当天补上并说明 |
| A 级超过 2 条不过 | 不通过 |
| B 级不过 | 记录，下一轮修，不阻断交付 |
| 声称「已验证」但拿不出验证记录 | 视为未验证，按不通过处理 |

**「验证记录」的定义**：具体命令 + 实际输出，或者截图、日志。口头说「测过了」不算。

## 七、本次事故对照（2026-11-27 数据丢失）

不遮掩，逐条对。

| 条目 | 是否违反 | 具体事实 |
|---|---|---|
| S1 数据与代码分离 | **违反** | `data.db` 一直放在 `daily-quadrant/` 目录内，每次发布被清 |
| S2 备份可恢复 | **违反** | 一次备份都没做，事故后无任何可恢复副本 |
| S3 密钥不泄漏 | 未违反 | `.gitignore` 与打包检查做到位了 |
| S4 部署后数据仍在 | **违反** | 从未在发布后重新登录验证，只看了接口返回 |
| A1 端到端 | 部分违反 | 走了浏览器流程，但没走「发布后」那一段 |
| A3 承诺兑现 | **违反** | 徽章写「05:42 提醒」，实际被静默规则拦掉不推 |
| B4 文档与代码一致 | **违反** | 规则写「2 天内提前推」，代码漏了第 2 天 |
| 铁律 4 不说没问题 | **违反** | 多次说「能用」「没问题」，属于不该给的保证 |

**八项里违反五项。** 其中 S1、S2、S4 三项直接导致数据不可恢复。

## 八、这个环境做不到的事（诚实声明）

不能又开一张空头支票。以下是现实限制，以及替代方案：

| 3-2-1 要求 | 本环境能力 | 替代方案 |
|---|---|---|
| 3 份副本 | 可以：生产库 + 每日备份 + 发布前备份 | 做到 |
| 2 种介质 | **做不到**：都在这台机器上 | 每月手动下载一份备份到本地电脑 |
| 1 份异地 | **做不到**：托管平台只给一个容器 | 同上：本地保存 = 事实上的异地 |
| 跨区域容灾 | **做不到** | 明确放弃，不假装有 |

**结论**：本项目的真实保障是「同一台机器上的 3 份副本」。机器整体丢失（换平台、容器彻底重建）时，只有你本地那份能救。所以——

**每月 1 号，我把最新备份下载给你存本地。** 这件事写进流程，不靠你提醒。

## 九、为什么不需要外接 AI

你问过要不要接 AI 来辅助判断任务优先级和提醒时间。

**不需要。** 理由：

1. 输入是结构化的（截止时间、重要度 1–9、难度 1–5），规则算得快、结果可复现、出错能查出是哪条规则算错了。
2. 接 AI 的代价：变慢（每次要等模型）、变贵、结果不稳定（同一输入两次输出可能不同），出了问题说不清原因。
3. AI 只在「把自然语言变成结构化数据」这一步有价值（「下午一点交串词」→ 时间 + 任务名）。这部分现在用规则做得够用，且可测——21 条回归用例能覆盖。

**什么时候才需要接**：任务量大到规则排不出合理顺序、或需要理解任务之间的依赖关系（「先写完报告才能做 PPT」）。现在没到这个量级。
